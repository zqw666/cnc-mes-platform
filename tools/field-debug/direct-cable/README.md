# 网线直连调试方案

> 前提：**开发机与工控机之间可以拉一根网线**。
> 有了这条物理链路，所有穿透方案（Tailscale / frp / 向日葵 / ToDesk）全都不需要，
> 现场禁 U 盘、内部平台只能传文字的限制也一并绕过 —— 网线本身就是一条私有高速通道。

地址规划：

| 网段 | 用途 | 本机（开发机） | 对端 |
|---|---|---|---|
| `192.168.125.x/24` | 工控机侧 | `192.168.125.210` | 工控机 `192.168.125.201` |
| `192.168.101.x/24` | 设备侧 | `192.168.101.200` | PLC `.10`　机床 `.51/.52/.53`　扫码枪 `.71` |

> 本机的有线网口（`以太网 4`）**早已配过 `192.168.101.200/24`**，说明以前就接过设备网。
> 现在只是网线没插。把线插上、跑一次 `connect-ipc.ps1`，两个网段会同时挂上。

## 一、三步走

### 第 1 步：插线 + 配 IP + 全面探测　（开发机，管理员）

```powershell
cd tools\field-debug\direct-cable
.\connect-ipc.ps1
```

自动完成：选有线网口 → 挂 `192.168.125.210/24` + `192.168.101.200/24`（不设网关）→
Ping 6 个关键设备 → 对通的主机做 9 个端口探测 → 输出结论。
结果同时存成 `connect-report.txt`，**纯文本，可以直接复制发回内部平台**。

找不到工控机时（它可能在别的地址），加扫网段：

```powershell
.\connect-ipc.ps1 -Sweep
```

调完想还原网络配置（会删掉上面两个 IP）：

```powershell
.\connect-ipc.ps1 -Restore
```

| 常用参数 | 作用 |
|---|---|
| `-Nic "以太网 4"` | 指定网口（名字或型号关键字），默认自动挑已插线的有线口 |
| `-NoIp` | 只探测，不动本机网络配置 |
| `-Sweep` | 扫 `192.168.125.1-254` 与 `192.168.101.1-254` 找存活主机（约 9 秒，实测） |
| `-Restore` | 撤销本脚本挂上的两个调试 IP，还原原样 |

### 第 2 步：让控制页能被外部打开　（工控机，管理员，只做一次）

后端只监听 `localhost` + `127.0.0.1:8888`（见 `web-ui/backend/Program.cs` 第 24–27 行），
所以网络通了浏览器也开不了页面。**不用改代码**，在工控机上做一次端口转发即可：

```powershell
# 把 ipc-setup.ps1 拷到工控机上（用下面的 serve-files.ps1 拉过去），然后：
.\ipc-setup.ps1
```

它做两件事：`netsh portproxy 0.0.0.0:8888 -> 127.0.0.1:8888` + 防火墙放行 8888。
之后开发机直接开：

```
http://192.168.125.201:8888/
```

| 常用参数 | 作用 |
|---|---|
| `-Status` | 只看状态（portproxy 规则 / 8888 监听 / 防火墙 / RDP / IP Helper），不改任何东西 |
| `-EnableRdp` | 额外开通远程桌面 3389 |
| `-Undo` | 撤销本脚本做的全部改动（含防火墙规则） |

> `portproxy` 依赖 **IP Helper(iphlpsvc)** 服务，脚本会自动确保它运行。
> **不建议随便开 3389**：远程桌面会抢占现场控制台画面，操作员会看到自己屏幕被接管。

### 第 3 步：传文件（不再受"只能传文字"限制）

在开发机上起一个下载服务，工控机用浏览器去拉 —— 工控机是客户端，
**不需要它开端口、不需要账号、不改任何设置**：

```powershell
.\serve-files.ps1 -Root "D:\部署包" -Port 8000
# 然后按提示的 URL，在工控机浏览器打开 http://192.168.125.210:8000/
```

支持大文件（流式发送）、目录浏览、目录穿越防护。Ctrl+C 停止。

> 反向（工控机 → 开发机）也一样：在工控机上跑 `serve-files.ps1`，
> 开发机去拉。或者直接 `\\192.168.125.201\c$`（若 445 已开放）。

### 第 4 步：出问题了，怎么知道 bug 在哪

**先记住这个前提：网络通了 ≠ 自动知道 bug 在哪。** 这个项目有两处会吃掉证据：

- `LogHelper` 默认 `FileEnabled=false` / `DatabaseEnabled=true` → **日志只写库、不落文件**；
- 代码里存在多处 `catch (Exception ex) { }` **空 catch** → 异常被静默吞掉，连库都不写。

于是故障的典型表现就是"流程跑一半就结束、什么都没有"。取证脚本就是解决这个：

```powershell
# 在工控机（管理员，证据最全）
.\collect-evidence.ps1 -OnIpc -DeployRoot "部署目录"

# 在开发机（网络通了就能用）
.\collect-evidence.ps1 -IpcIp 192.168.125.201
```

产出 `evidence-<时间戳>.md`，一次性抓四层证据：

| 层 | 内容 | 能回答什么问题 |
|---|---|---|
| 入口 | 8888/3389/445/1433/4026 开没开、控制页 HTTP 状态 | 到底能不能进得去 |
| 部署真实性 | 主程序与 `subs/*.exe` 的修改时间对比、`config.json` 关键项 | 跑的是不是你手上那份代码？有没有只换一半？ |
| **数据库** | 表存在性 + `work_flow` 顺序 + `workflow_step` + `workflow_log` + `process_log` | **程序最后承认做过什么** |
| 进程与环境 | 主程序是否在跑、`stop.flag`、`portproxy`、系统事件日志里的 .NET 异常 | 有没有硬崩溃（绕过所有空 catch 的证据） |

> 脚本**不假设数据库 schema**：先用带排序的 SQL，失败就退化成 `select *`，
> 并把真实列名打出来（实测本库 `work_flow` 的列是 `processname` 而不是 `step_name`）。
> 只读，不改配置、不写库。

**读报告的三步法**（脚本末尾也会打印）：

1. 看 `workflow_step` 最后一条 —— 有 `status` 就知道卡在哪一步；**表为空**说明异常发生在登记步骤之前；
2. 看 `process_log` / `workflow_log` 最后一条的时间与内容 —— 它之后的第一个业务动作就是嫌疑点；
3. **用 PLC 信号交叉验证**（不依赖任何日志）：读 `robot.taskNumber`(D100) 有没有下发、值对不对；
   读 `taskStart`(104.00) 有没有脉冲；读 `robotmessage.clampposstatus` 有没有被写。
   日志被吞掉时，**PLC 侧的动作序列是唯一客观证据** —— 任务号算错这类 bug 会直接暴露在这里。

> 如果四层全空（表空 + 日志无 + 事件无 + PLC 无动作），基本可断定异常发生在最早的配置加载阶段，
> 且被空 catch 吞掉 → 这时必须开文件日志或上断点，**靠库是查不出来的**。

## 二、四种调试通道对比

| 通道 | 前提 | 能力 | 代价 / 风险 |
|---|---|---|---|
| **A. 浏览器开控制页** ⭐ | 工控机跑一次 `ipc-setup.ps1` | 看 / 改线体配置、触发流程 | 无。**首选**，不干扰现场画面 |
| **B. 远程桌面 3389** | 工控机 `-EnableRdp` | 完整桌面：跑 VS、看日志、开本地浏览器 | **会踢掉现场控制台画面**，生产时慎用 |
| **C. 文件推送 8000** | 无（开发机起服务即可） | 部署包 / 日志 / 图片双向传 | 无。首次需在工控机允许防火墙 |
| **D. 远程调试 4026** | 工控机跑 `msvsmon.exe`，且 PDB 与 exe 版本一致 | 真正下断点调试 | 要同步 PDB；`MachineMonitor.exe` 重启会中断生产 |
| **E. 本机直跑** | 开发机接设备网（已满足） | 开发机上直接跑 `MachineMonitor.exe` 连真 PLC / 机床 | ⚠️ **不能与工控机同时运行**：同一台 PLC 两个主站会指令打架 |

**E 值得单独说一句**：既然开发机已经在设备网里，`192.168.101.10` 的 PLC、`.51/.52/.53` 的机床都能直连，
你可以把整个运行环境搬到开发机上跑，改代码 → 立刻验证，完全不碰现场那台工控机。
唯一红线：**跑之前先确认工控机上的 `MachineMonitor.exe` 已停止**，否则两个进程抢同一台 PLC。

## 三、脚本清单

| 脚本 | 在哪运行 | 作用 | 要管理员吗 |
|---|---|---|---|
| `connect-ipc.ps1` | 开发机 | 配双网段 IP + Ping/端口全探测 + 结论 + 出报告；`-NoIp` 只探测、`-Sweep` 扫段、`-Restore` 撤销 | 配 IP / 撤销需要 |
| `serve-files.ps1` | 开发机（或工控机） | 极简 HTTP 文件下载服务，推文件给对端 | 否 |
| `ipc-setup.ps1` | 工控机 | portproxy 8888 + 防火墙 + 可选 RDP，可 `-Status` / `-Undo` | 是 |
| `collect-evidence.ps1` | 工控机（`-OnIpc`）或开发机 | **取证**：表存在性 + 步骤状态 + 日志 + 部署核对 + 事件日志，出 Markdown 报告 | 否（只读），但库写权限建议给 |

## 四、排障对照表

| 现象 | 原因 | 处理 |
|---|---|---|
| 网口状态 `Disconnected` | 网线没插 / 对端没通电 | 插好线，指示灯亮起 |
| 两个网段都 ping 不通 | 网线插错口 / 交换机不同网段 | `-Sweep` 扫一遍；或到工控机 `ipconfig` 看它实际地址 |
| 能 ping 通工控机但 8888 关闭 | 后端只监听 localhost | 工控机跑 `ipc-setup.ps1` |
| 8888 也不通但 445 通 | 网络没问题，只是没转发 | 同上；或走 RDP 在工控机本地开 `http://localhost:8888/` |
| 网页打开白屏 / 配置不生效 | 后端读的库与预期不一致 | 见项目记忆：MySQL `qianduantest` 才是真实生产库，`config.json` 的 `database.type` 要对上 |
| `ipc-setup.ps1 -Status` 里 8888 无监听 | `MachineMonitor.exe` 没在跑 | 先确认主程序已启动 |

## 五、还有一个坑：`config.json`

`config.json` 必须与 `MachineMonitor.exe` 同目录，子程序在 `subs/` 下向上逐级查找。
用 `serve-files.ps1` 推文件时注意：**exe、`subs/`、`lib/`、`sections/`、`config.json` 要整套一起换**，
不要只换单个文件 —— 项目记忆里有记录：Debug 与 Release 两处的 `eman.host` 曾经不一致
（`.129.243` vs `.128.243`），`database.type` 也被单独改成过 `sqlserver`。
换完在工控机上跑 `ipc-setup.ps1 -Status` 确认服务正常监听再收工。
