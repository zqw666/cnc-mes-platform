# 合并程序上传改善方案（load_machine / 西门子 4 工位）

> 整理时间：2026-08-05
> 涉及代码：`web-ui/load_machine/load_machine/transfer.cs`、`web-ui/load_machine/load_machine/Program.cs`
> 参考项目：`D:\桌面\GreeCmmSys-FINAL`（已确认其"合并程序"机制）

---

## 1. 背景：为什么要"合并程序"

- 每台西门子机床 4 个工位，一次流程上 1 件，**放满 4 件才启动加工**（前 3 件只记录待加工）。
- 4 个工位 = 4 个不同工件，各有独立 NC 程序（共享服务器上 `<工件名>.nc`）。
- 西门子机床一次只能执行**一个主程序**，因此需要把 4 段程序合并成 1 个主程序上传，一次启动加工 4 件。

## 2. 现状与问题

### 2.1 现状（代码里实际是什么）

`transfer.cs` 的 `RunTransferProcess(ip, workpiecename)`：

```
共享服务器 <工件名>.nc
  → 本地临时目录 <工件名>.nc
  → 机床 SMB 共享 \IP\C\NCFiles\<工件名>.nc
```

- 只接收**单个工件名**，做单文件复制，**没有合并逻辑**。
- `Program.cs` 的 `HandleUploadProgram` 里 `needMerge = totalPos > 1` 只用于打日志（"需合并程序后再上传"/"（已合并）"），并不真正合并。
- 代码 TODO 已注明：`RunTransferProcess` 需替换为实际的合并上传方法。

### 2.2 问题清单

| # | 问题 | 影响 |
|---|------|------|
| 1 | 无合并逻辑，4 个工件程序不会合成一个主程序 | 放满 4 件后机床无法一次加工 4 件 |
| 2 | 上传目标用 SMB `\IP\C\NCFiles`，而西门子机床实际用 SFTP（WinSCP，`/card/user/sinumerik/data/mnt/usercf/spf.dir/`） | 现场上传路径大概率不对 |
| 3 | 机床本地程序名用 `<工件名>.nc`，西门子主程序固定名应为 `NCPROGRAM.mpf` | 程序名不匹配，机床找不到主程序 |
| 4 | 上传成功后没有"启动加工"衔接（现在由 `Program.cs` PLC 启动，但文件若没传对则启动无意义） | 流程不闭环 |
| 5 | `transfer.cs` 里 `UpdateRackAdministrateWorkstate` 用 `workpiecename` 列，真实库 `rack_administrate` 无此列（工件名存 `rfid`） | 该更新会静默失败（与 `Program.cs` 已修的一致） |

## 3. 参考实现：GreeCmmSys-FINAL（已确认）

`D:\桌面\GreeCmmSys-FINAL` 是同类西门子 4 工位自动线项目，其合并程序机制：

- **合并程序是预生成成品**：`D:\WorkAuto\MergeProgram\F01.mpf ~ F012.mpf`（`FrmRack.cs` `ReturnProPath`），按料架层 1-12 预先做好，每个 `.mpf` 是一次启动该层 4 个磁盘的西门子主程序。
- **运行时只做"选文件 + 改名 + 上传"**：
  1. 按料架层选 `F0X.mpf`
  2. 复制为 `D:\WorkAuto\NcProgram\NCPROGRAM.mpf`
  3. `FileSiemens`（WinSCP/SFTP）删除机床旧文件后上传到 `/card/user/sinumerik/data/mnt/usercf/spf.dir/NCPROGRAM.mpf`
- **启动加工由 PLC/机器人触发**：该项目本身不启动机床；机器人 `GreeRobot.SendWork(task)` 写 `DM100=任务号`、置位 `200.00`，放完 4 个后 PLC 发启动命令（与 ERP 现定方案一致）。
- **任务号规则印证候选方案**：`ReturnTask` 层 1-6 → 101-106、层 7-12 → 121-126，与 `GetPlaceTaskNo` 候选"机床号×100+工位号"同风格。

## 4. 改善方案（建议）

### 4.1 总体思路

把 `transfer.cs` 从"单文件 SMB 复制"改为"**按规则选合并文件 → 改名 NCPROGRAM.mpf → SFTP 上传**"，配置驱动，不改数据库。

### 4.2 配置新增（`config.json`）

```json
"nc_server": {
  "root_path": "\\192.168.1.100\share",        // 共享服务器根（已有）
  "local_temp": "D:\\nc_temp",                    // 本地临时目录（已有）
  "merge_dir": "D:\\WorkAuto\\MergeProgram",    // 合并程序目录（新增）
  "merge_file": "NCPROGRAM.mpf",                    // 上传到机床的固定主程序名（新增）
  "merge_remote_path": "/card/user/sinumerik/data/mnt/usercf/spf.dir/",  // 机床远程目录（新增）
  "machine_type": "siemens"                         // 传输方式：siemens=SFTP；roders=SMB（新增）
}
```

### 4.3 `transfer.cs` 改造点

```
RunTransferProcess(ip, workpiecename, macnum, worknum, 是否满4件)
  ├─ 未满4件：不传文件（直接返回 true，避免每件都传）
  └─ 满4件：
      ├─ 选合并文件：merge_dir + 规则文件名（见 4.4）
      ├─ File.Copy(合并文件, local_temp + NCPROGRAM.mpf, true)
      ├─ siemens 模式：WinSCP 删旧 → 上传到 merge_remote_path
      ├─ roders 模式：保留原 SMB 复制（改动不回归）
      └─ 返回是否成功
```

新增/调整：
- 重载 `RunTransferProcess(ip, macnum, 工件列表)`，由 `Program.cs` 满 4 件时传入该机床 4 个工件名。
- 新增 `MergeProgramPath(工件列表)`：按 4.4 规则返回合并文件路径。
- 新增 `SiemensUpload`（WinSCP）：删除远程 `merge_remote_path + merge_file` → `PutFiles` 上传。
- `UpdateRackAdministrateWorkstate` 列名改为 `rfid`（与真实库一致）。
- 与 PLC 启动衔接：上传成功后才由 `Program.cs` 发启动命令（现状已如此，保持）。

### 4.4 合并文件命名规则（待现场确认，默认按参考实现）

参考 GreeCmmSys 按"料架层"命名 `F01.mpf ~ F012.mpf`。ERP 侧两个候选：

- **方案 A（推荐，贴近参考）**：按机床号+批次生成 `M{机床号}B{batch}.mpf`（如 `M1B1.mpf`），放满 4 件时用当前批次号。
- **方案 B（按参考原样）**：沿用 `F01.mpf ~ F012.mpf` 按料架层，需要 ERP 有"料架层"概念映射到 4 件工件。

> 确认后只需实现 `MergeProgramPath` 一处映射。

## 7. 结论

- "合并程序"在参考项目中是**预生成 `.mpf` 成品 + 按层选用 + SFTP 上传**，不是运行时拼接。
- ERP 侧最小改动：`transfer.cs` 满 4 件时按规则选合并文件 → 改名 `NCPROGRAM.mpf` → SFTP 上传（西门子）/SMB（罗德斯），随后保持 PLC 启动。
- 需现场确认：合并文件命名规则、`.mpf` 样例、SFTP 凭证。确认后即可实现。
