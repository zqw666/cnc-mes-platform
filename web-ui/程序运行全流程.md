## 1. 整体架构

```
┌────────────────────────────────────────────────────────────┐
│                         前端                               │
│   默认入口: http://localhost:8888/  → index.html           │
│   并行版本: http://localhost:8888/index_vue.html           │
│   index.html = 模块化 JS（sections/*.js + main.js）        │
│   index_vue.html = Vue 2 + Element UI（app.js）            │
│   板块: 主界面 / 任务管理 / 料架管理 / 日志查询 / 线体配置  │
└──────────────────────────┬─────────────────────────────────┘
                           │ HTTP REST API (GET/POST, CORS 开放)
                           ▼
┌────────────────────────────────────────────────────────────┐
│               后端 MachineMonitor.exe（.NET Framework）    │
│   Program.cs: 初始化 + HttpListener 事件循环               │
│   Router.cs:   路由分发                                    │
│   Controllers: Dashboard/Workflow/Log/Config/Machine/Rack  │
│   Services:    WorkflowService / ConfigService             │
│   Repository:  DatabaseRepository（建库建表/补列）          │
│   日志:        LogHelper → 控制台 + logs/*.log + DB        │
└──────────────────────────┬─────────────────────────────────┘
                           │
        ┌──────────────────┼──────────────────┐
        ▼                  ▼                  ▼
┌──────────────┐   ┌──────────────┐   ┌──────────────────┐
│ PLC (欧姆龙)  │   │ 机床通讯层    │   │ 数据库            │
│ FINS/UDP     │   │ 西门子 OPC UA│   │ MySQL qianduantest│
│ 指挥机器人动作 │   │ 罗德斯 TCP   │   │ SQL Server eman   │
└──────────────┘   └──────────────┘   └──────────────────┘
```

### 三层架构

| 层 | 组件 | 职责 |
|------|------|------|
| **展示层** | `frontend/index.html`、`frontend/index_vue.html` | 机床状态、料架、实时日志、线体配置、工作流控制 |
| **调度层** | `backend/MachineMonitor.exe` | HTTP 服务、API、工作流编排、子进程启动/暂停/停止 |
| **执行层** | `backend/subs/*.exe`（如 `load_machine.exe`） | 各工序独立进程，连接 PLC + 机床 + 数据库 |

子进程不直接读本地 `config.json` 优先路径，而是通过公共库 `ConfigClient.FetchConfig()` 先请求后端 `GET /api/config/raw`，后端不可达时回退到本地配置文件。

## 2. 后端启动流程

### 2.1 初始化顺序

```
MachineMonitor.exe 启动
  │
  ├─ 1. AppState 静态初始化
  │     ├─ 定位 config.json（exe 同级目录，找不到则用 AppDomain BaseDirectory）
  │     ├─ server.port          → HTTP 端口（默认 8888）
  │     ├─ server.logCapacity   → 内存日志上限（默认 1000）
  │     └─ database 节点        → MySQL / SQL Server 连接串
  │
  ├─ 2. EnsureSubDir()
  │     └─ 创建 backend/subs/ 子进程目录
  │
  ├─ 3. DatabaseRepository.EnsureDatabaseAndTables()
  │     ├─ MySQL: 自动创建数据库（utf8mb4）
  │     ├─ SQL Server: 自动创建数据库
  │     ├─ 检查并创建表: macmessage / macworkposstatus / process_flow /
  │     │   process_status / work_flow / robotmessage / following_rack /
  │     │   rack_administrate / grippers / knife_rack / workflow_log
  │     └─ rack_administrate 缺失 materialname / programname 时自动补列
  │
  ├─ 4. EnsureDirectories()
  │     └─ 创建 exe 同级 logs/ 日志目录
  │
  ├─ 5. WorkflowService.EnsureSteps()
  │     └─ 向 work_flow 表插入/启用 9 个默认步骤（status=1, priority=0）
  │
  ├─ 6. 启动 HTTP 服务
  │     ├─ 监听 http://127.0.0.1:8888/
  │     ├─ 静态文件 + REST API
  │     └─ 事件循环 Task.Run(Router.Handle(ctx))
  │
  └─ 7. 输出就绪日志
        [MachineMonitor] HTTP 服务已启动 http://localhost:8888/
```

### 2.2 关键启动代码（Program.cs 简化）

```csharp
static void Main(string[] args)
{
    // AppState 静态构造已加载 config.json 并生成连接串
    EnsureSubDir();                          // subs/
    DatabaseRepository.EnsureDatabaseAndTables();
    EnsureDirectories();                     // logs/
    WorkflowService.EnsureSteps();           // work_flow 默认步骤

    var listener = new HttpListener();
    listener.Prefixes.Add($"http://127.0.0.1:{AppState.Port}/");
    listener.Start();

    while (true)
    {
        var ctx = listener.GetContext();
        Task.Run(() => Router.Handle(ctx));
    }
}
```

### 2.3 启动细节

- `AppState.DbType` 来自 `database.type`（`mysql` / `sqlserver`），MySQL 默认 `localhost:3306/qianduantest/root/123456`，SQL Server 默认 `localhost:1433/eman/sa/123456`。
- `EnsureDatabaseAndTables` 只为部分表提供建表 SQL；`macworkposstatus`、`robotmessage`、`following_rack` 等表在真实库中预置，后端只检查存在性。
- `EnsureRackAdministrateColumns` 会在 MySQL 下执行 `SHOW COLUMNS FROM rack_administrate` 并补 `materialname`、`programname` 两列。

## 3. API 一览

| 接口 | 方法 | 说明 |
|------|------|------|
| `/` | GET | 返回 `index.html` |
| `/index_vue.html` | GET | 返回 Vue 版前端 |
| `*.js / *.css / *.html / *.png / *.jpg / *.ico` | GET | 从 exe 同级目录返回静态文件 |
| `/api/dashboard` | GET | 机床列表 + 今日加工/未加工统计 + 工作流状态 |
| `/api/workflow/status` | GET | 工作流运行/暂停状态 + 步骤列表 |
| `/api/workflow/start` | POST | 启动工作流 |
| `/api/workflow/stop` | POST | 停止工作流（取消等待中的子进程） |
| `/api/workflow/pause` | POST | 暂停工作流（步骤之间生效） |
| `/api/workflow/resume` | POST | 恢复工作流 |
| `/api/config` | GET/POST | 读取归一化配置 / 保存配置 |
| `/api/config/raw` | GET | 返回 config.json 原始内容 |
| `/api/config/debug` | POST | 调试回显（仅记录收到的 JSON） |
| `/api/sub/log` | POST | 子进程日志上报（写 workflow_log + 内存队列） |
| `/api/rack/status` | GET/POST | 读取料架状态 / 更新料位状态 |
| `/api/rack/create` | POST | 在 config.json 中新增料架 |
| `/api/machine/create` | POST | 在 config.json 中新增机床 |
| `/api/machine/start` / `pause` / `stop` | POST | 更新 `macmessage.workstate` 及停机字段 |

注意事项：

- `Router` 统一添加 CORS 头（`Access-Control-Allow-Origin: *`），支持 GET/POST/OPTIONS。
- `/api/logs` 由 `LogController.GetLogs(raw)` 处理，`raw` 只从 POST body 读取；前端 `GET /api/logs?page=1&pageSize=50` 的查询参数目前不会被解析，实际始终按 `page=1, pageSize=50` 返回内存日志。
- 未匹配的路径返回 `{ success:false, message:"未找到接口" }`。

## 5. 工作流调度

### 5.1 状态与命令

| 命令 | 后端行为 |
|------|---------|
| start | 已在运行则拒绝；清空内存日志队列；创建 `CancellationTokenSource`；后台 `Task.Run(RunWorkflow)` |
| pause | 设置 `WorkflowPaused=true`，在步骤之间生效 |
| resume | 清除暂停标记 |
| stop | `WorkflowCts.Cancel()`，并立即复位运行/暂停标记 |

### 5.2 步骤来源

```csharp
// WorkflowService.GetEnabledSteps()
// 优先 work_flow：status=1 ORDER BY priority DESC, id ASC
// work_flow 无数据时回退 process_flow：status=1 ORDER BY id
```

启动时 `EnsureSteps()` 会把以下 9 个默认步骤 upsert 到 `work_flow`：

| 步骤名 | 显示名 | 子进程文件 |
|--------|--------|-----------|
| `rackoperate` | 料架操作 | `rackoperate.exe` |
| `scan` | 扫描 | `scan.exe` |
| `preparematerial` | 备料 | `prepare_material.exe` |
| `loadmachine` | 上机 | `load_machine.exe` |
| `unloadmachine` | 下机 | `unload_machine.exe` |
| `unloadmaterial` | 下料 | `unload_material.exe` |
| `materialknife` | 备刀 | `prepare_knife.exe` |
| `changemachine` | 换机 | `change_machine.exe` |
| `changeknife` | 换刀 | `change_knife.exe` |

### 5.3 执行流程

```
RunWorkflow(ct)
  │
  ├─ 读取启用的步骤列表（按 priority DESC, id ASC）
  ├─ while (!ct.IsCancellationRequested)
  │    ├─ foreach step:
  │    │    ├─ 若 WorkflowPaused → 等待恢复
  │    │    ├─ UpdateStepStatus(running) 写 workflow_step
  │    │    ├─ 启动 subs/<step>.exe（无命令行参数，CreateNoWindow）
  │    │    ├─ 等待子进程退出
  │    │    ├─ UpdateStepStatus(completed) 写 workflow_step
  │    │    └─ 记录“开始执行/步骤完成”日志
  │    └─ Task.Delay(1000, ct)
  │
  └─ 注意：当前实现是持续循环，不是执行一轮就结束
```

当前 `RunWorkflow` 会无限循环执行启用的步骤；停止通过取消令牌打断 `WaitForExit` 和暂停等待。

### 5.4 日志链路

```
子进程 Program.cs / transfer.cs
  → LogHelper.Info/Warn/Error/Success(...)
      ├─ Console.WriteLine（控制台）
      ├─ 写 logs/yyyy-MM-dd_<step>_<level>.log（文件）
      └─ Task.Run(HTTP POST /api/sub/log)
           └─ backend LogController.ReceiveSubLog
                └─ WorkflowService.WriteStepLog
                     ├─ AppState.AllLogs 内存队列（上限 1000 条，供 /api/logs 实时展示）
                     └─ INSERT INTO workflow_log (step_name, level, content, created_at)
```

后端自身（`Program.cs`、`Router.cs`、`WorkflowService.cs` 等）也统一使用 `LogHelper`。

### 5.5 步骤状态落库说明

- 步骤执行状态写入 `workflow_step`：开始步骤时写 `running`，正常完成后写 `completed`；`step_name` 唯一，MySQL 用 `ON DUPLICATE KEY UPDATE`，SQL Server 用 `IF NOT EXISTS ... ELSE UPDATE`。
- 日志统一写入 `workflow_log`（注意不是旧的 `process_log` / `runlog`）。
- `process_status` 是 Dashboard 的加工统计表（process_status=0 未加工、2 已完成），不再混入步骤状态。

## 6. 上机子进程详解（上机为例）

### 6.1 启动与配置

```
load_machine.exe 启动
  ├─ LogHelper.Info("上机流程分包启动")
  ├─ ConfigClient.FetchConfig(ApiBase)     ← GET /api/config/raw
  │    └─ 失败回退本地 config.json
  ├─ ExtractConfig(cfg)
  │    ├─ database → ConnStr
  │    ├─ plc.ip / plc.port
  │    ├─ plc.signals.robot.taskNumber → PlcDm（默认 D100 → 100）
  │    ├─ plc.signals.robot.taskStart   → TaskStartAddr
  │    ├─ plc.signals.robot.taskDone    → TaskFinishAddr
  │    ├─ plc.signals.robot.photo       → RobotEleAddr
  │    ├─ plc.signals.machine.startTaskNo → MachineStartTaskNo
  │    ├─ line.gripperType → 固定爪判断
  │    └─ grippers[] → 夹爪配置列表
  ├─ InitMachines(cfg)
  │    └─ machines 字典 → Macfactory 创建西门子/罗德斯实例
  ├─ LogHelper.Configure(stepName, displayName, apiBase)
  ├─ 连接数据库
  ├─ PLC.Connect(PlcIp, PlcPort)          ← 失败退出
  └─ Waitmaclist()                        ← 待机机床
```

### 6.2 主流程步骤（当前实现）

```
1. 查待机机床
   SELECT * FROM macmessage WHERE status!=0
   再逐台 GetMacStatusSafe(id)=="reset"
   且 workpiecename=="" 且 workpieceworkstate=="0"

2. 判断工件来源
   有随行台（line.shuttleExists 非空）:
     following_rack WHERE posstatus=2 AND workpieceworkstate=0
   无随行台:
     robotmessage WHERE id=1 AND workpiecestatus=0 的 workpiecename

3. 置换夹爪 ChangeGripper()
   fixed-single / fixed-double → 跳过
   快换爪 → 类型不匹配时: 放工件/放当前爪/抓目标爪

4. 选第一台待机机床，一次流程只上 1 件
   worknum = GetMacFirstEmptyWorknum(macnum)
   （自动按 stationCount 补齐 macworkposstatus 空工位行）

5. 有随行台 → ExecuteTask(随行台料位ID) 抓取
   更新 following_rack(posstatus=1)
   更新 robotmessage(workpiecename, workpiecestatus=2)

6. 放置工件到机床
   OpenMachineDoorIfRoders()（罗德斯才开门）
   placeTaskNo = GetPlaceTaskNo(macnum, worknum)  ← 当前返回 macnum
   ExecuteTask(placeTaskNo)
   CloseMachineDoorIfRoders()（罗德斯才关门）
   更新 robotmessage(null, workpiecestatus=1)

7. 工位表记录
   UPDATE macworkposstatus SET workpiece_name=..., workpiece_status=0
   WHERE mac_name=... AND worknum=...

8. 放满判断
   还有空工位 → 记录“未满，等待下次上机”并退出（不启动加工）
   无空工位   → HandleUploadProgram()

9. HandleUploadProgram()
   transfer.RunTransferProcess(ip, workpiecename)  ← 上传 NC
   西门子且 MachineStartTaskNo>0 → ExecuteTask(MachineStartTaskNo)（PLC 启动）
   否则 → MacStartProcessSafe(macnum)（机床通讯层启动）

10. 启动成功后
    UPDATE macworkposstatus SET workpiece_status=1（该机床所有有件工位）
    按 rfid 更新 rack_administrate.workstate=1
```

### 6.3 ExecuteTask 通讯详解

```csharp
static bool ExecuteTask(int tasknum)
{
    // 1. 复位任务开始信号
    if (!string.IsNullOrEmpty(TaskStartAddr))
        Plc.WriteWR(TaskStartAddr, 0);

    // 2. 写任务号到 DM
    if (!Plc.WriteDM(PlcDm, tasknum)) return false;

    // 3. 置位任务开始信号
    if (!string.IsNullOrEmpty(TaskStartAddr))
        if (!Plc.WriteWR(TaskStartAddr, 1)) return false;

    // 4. 等待任务完成信号（最多 300 秒）
    if (!string.IsNullOrEmpty(TaskFinishAddr))
    {
        int waitCount = 0;
        while (!Plc.ReadWR(TaskFinishAddr) && waitCount < 3000)
        {
            Thread.Sleep(100);
            waitCount++;
        }
        if (!Plc.ReadWR(TaskFinishAddr)) return false;
    }
    return true;
}
```

任务号对应关系：

| 场景 | 任务号 |
|------|--------|
| 随行台抓取 | 随行台料位 ID |
| 放置到机床 | `GetPlaceTaskNo(macnum, worknum)`，当前固定返回 `macnum` |
| 西门子 PLC 启动加工 | `plc.signals.machine.startTaskNo`（当前占位 300 的模拟值，运行时配置中待填） |

### 6.4 上传与启动加工

`transfer.cs` 当前实现：

- 默认共享服务器：`\\192.168.1.100\share`
- 默认本地临时目录：`D:\nc_files`
- 默认机床 NC 目录：`C:\NCFiles`
- 文件规则：`工件名 + ".nc"`，共享服务器 → 本地 → 通过 SMB 复制到机床
- `LoadConfig()` 会尝试读取 `share_server`（`path` / `local_temp` / `machine_nc_path`），当前 `config.json` 里键是 `nc_server`，因此实际仍用上述硬编码默认值
- `HandleUploadProgram()` 中有 TODO：4 工位“合并程序”逻辑尚未实现，目前仍按单个工件名上传 `*.nc`

启动加工：

- 西门子（`type=siemense`）且配置了 `plc.signals.machine.startTaskNo` → 复用 `ExecuteTask`，写 DM 任务号 → 置开始信号 → 等完成信号
- 其他情况 → `MacStartProcessSafe(macnum)`（罗德斯为真实实现，西门子当前为空实现，需保持配置走 PLC 通道）

## 7. 设备通讯层

### 7.1 PLC（欧姆龙 FINS/UDP）

| 操作 | 方法 | 说明 |
|------|------|------|
| 写 DM | `Plc.WriteDM(100, 任务号)` | 机器人任务号 |
| 写 WR 位 | `Plc.WriteWR("104.00", 0/1)` | 任务开始/复位 |
| 读 WR 位 | `Plc.ReadWR("205.00")` | 任务完成信号 |
| 连接 | `Plc.Connect(ip, port)` | 默认 `192.168.1.1:9600` |

信号地址来自 `plc.signals.robot`：

```json
"robot": {
  "photo": "",
  "taskStart": "104.00",
  "taskDone": "205.00",
  "taskNumber": "D100",
  "error": "",
  "safePos": "",
  "estop": ""
}
```

`taskNumber` 只取数字部分（去掉 `D` / `DM`），如 `D100` → `100`。

### 7.2 西门子（Siemens）— OPC UA

- 通过 `MacCommunicate` 的 `Macfactory` 创建 `siemense` 实例
- 支持配置 `sessionUrl`（如 `opc.tcp://ip:4840`）、`username`、`password`
- 当前上机流程的“启动加工”走 PLC 通道，不依赖 `Siemence.MacStartProcess()`（该方法仍为空实现）

### 7.3 罗德斯（Roders）— TCP

- `roders` 实例通过 TCP 与机床通讯
- 上机时先 `OpenDoor`（创建 TCP 服务器等待机床连接），放件后 `closeDoor`
- 启动加工走 `MacStartProcess()`

- `1`：`siemense`，`192.168.101.53:4840`，4 工位

## 8. 数据库表结构

### 8.1 后端自动维护的表

| 表名 | 用途 | 建表方式 |
|------|------|---------|
| `macmessage` | 机床主表（machinename/machineip/workstate/status/error_message） | 后端提供建表 SQL |
| `process_flow` | 普通流程备选表 | 后端提供建表 SQL |
| `work_flow` | 定制工作流（processname/status/priority） | 后端提供建表 SQL，启动时 upsert 默认步骤 |
| `process_status` | 加工/流程状态统计（process_name/process_status/process_start_time/process_end_time） | 后端提供建表 SQL |
| `workflow_log` | 统一日志表（step_name/level/content/created_at） | 后端提供建表 SQL |
| `workflow_step` | 步骤执行状态（step_name 唯一，last_status/last_message/last_time） | 后端提供建表 SQL |
| `rack_administrate` | 料架料位（id/racknum/racktype/name/rows/cols/scanstatus/posstatus/workstate/rfid/verifyid/priority/workpiecename/materialname/programname） | 后端提供建表 SQL，启动时补 materialname/programname |
| `grippers` | 夹爪配置 | 后端提供建表 SQL |
| `knife_rack` | 刀库料位 | 后端提供建表 SQL |

### 8.2 真实库预置、代码实际使用的表

#### macworkposstatus — 机床工位表

```sql
-- 代码实际使用的字段
mac_name        VARCHAR      -- 机床名称（对应 macmessage.machinename）
worknum         INT          -- 工位号
workpiece_name  VARCHAR      -- 工位上的工件
workpiece_status INT         -- 0=待加工, 1=加工中
```

#### following_rack — 随行台

```sql
id                 INT        -- 料位号（也是任务号）
workpiecename      VARCHAR    -- 工件名称
workpieceworkstate INT        -- 工件状态
posstatus          INT        -- 0=空, 1=已占用, 2=待上机
```

#### robotmessage — 机器人状态

```sql
id               INT
clampname        VARCHAR     -- 当前夹爪名称
clampstatus      INT         -- 夹爪类型
clampposstatus   INT         -- 夹爪有无
workpiecename    VARCHAR     -- 夹爪上的工件
workpiecestatus  INT         -- 实际约定: 0=夹爪有待上机工件, 1=放置后无工件, 2=随行台抓取后标记
```

### 8.3 使用约定

- 上机时按 `macworkposstatus.mac_name = macmessage.machinename` 关联，工位行由 `EnsureMacWorkPosRows()` 按 `stationCount` 补齐。
- 料架回写按 `rack_administrate.rfid = 工件名` 更新 `workstate`。
- 日志统一进 `workflow_log`；`process_log`、`runlog`、`workflow_step` 已不是后端当前创建/写入的表。

### 9.4 保存链路

前端保存配置 → `POST /api/config`，后端 `ConfigService.SaveConfig` 合并以下键：

- `database`、`plc`、`line`、`racks`、`grippers`
- `machines`：前端数组转 `{ id: {...} }` 字典，字段统一为 `type/number/ip/port/stationCount/ncPath/sessionUrl/username/password`
- `workflow`：逐条 upsert 到 `work_flow`（`status` 由 enabled 决定，`priority` 存优先级）
- 最终写回 `config.json`

子进程侧 `ConfigClient.FetchConfig()` 优先 `GET /api/config/raw`（超时 3 秒），失败后从当前目录向上查找 `config.json`。
