1系统全貌

一套跑在工控机上的单体服务：C# 提供 HTTP 接口和静态页面，前端是无构建的原生 JS，14 个独立子程序 exe 承担具体动作，通过原生 DLL 与设备通讯。

21HTTP 接口
14子程序 exe
7Controller
8888服务端口

六层结构

前端
原生 HTML / CSS / JS（script.js 约 93 KB）+ Vue 2.7.14 + Element UI 2 + amis 6.13 + SortableJS · 无构建链
接口层
HttpListener 监听 8888 · Router.cs 手写 if-else 分发（110 行）· 无 Web 框架
业务层
Controllers 7 个 / Services 2 个（Config、Workflow）/ Repository 1 个 · 无 DI、无 ORM
数据层
MySQL 8.x 库 qianduantest（代码兼容 SQL Server）· 编排配置存 flow.json
执行层
14 个独立 exe，各自 Main() 跑完退出，进程间零共享 · ProcessStartInfo + WaitForExit 调度
设备层
PLC.dll · mcOMRON · Siemens.OpcUA · Fwlib32（Fanuc）· Rodersoperate · MacCommunicate
上四层是自己的代码，可以改；下两层是外部约束，改不动也不该改。

4副本现状

本机同时存在 5 份副本，只有一份是主线。这是当前最大的技术债 —— 靠文件夹名管版本，改坏了无法回滚。

路径状态判断依据

D:\桌面\web-ui旧版无 frontend/，页面在根目录
D:\桌面\前后端分离 - 副本副本目录名带“副本”
D:\桌面\11\前后端分离早期2026-07 时间戳

建议第一步：补 Git。五份副本归一，成本半天。没有它，后面所有改动仍然是在“改坏了没法回滚”的状态下进行。

5阅读路线

按“从外到内、从能跑到原理”的顺序，约 3 天能形成完整认知。第 3 步是关键：彻底搞通一条链，剩下 20 个接口都是同一套路。

步做什么时间得到什么
1编译启动，把页面每个功能点一遍1 小时知道它长什么样、有哪几个功能
2读 Router.cs（只有 110 行）30 分钟接口全貌，即上一节那张表
3跟一条最简单的链到底：料架状态2 小时打通“页面→API→Controller→Repository→SQL→返回→渲染”
4读 Services/WorkflowService.cs半天编排怎么启动、怎么等、怎么判断成败
5读 scan 子程序的 Main半天子程序怎么被调用、参数从哪来
6读 flow.json 与 lowcode/workflow-designer.html半天编排数据怎么存、界面怎么读它

6不要看什么

接手最容易犯的错是“想把所有代码都读一遍”。这几处读了也没有收益，能省两天。

别看为什么
script.js（93 KB）全局变量堆出来的，通读没有意义。需要时按函数名 grep
除 scan 外的 13 个子程序结构相同，看懂一个就够
所有设备 DLL二进制黑盒，看不了也不用看
Node 的 server.js历史遗留，主链路不走它（主链路在 C# 的 8888）
三个编排页里的两个先定一份主线，其余归档，不用三份都读

7低代码能做什么

低代码降低的是“编排成本”，不是“开发成本”。它只覆盖特定一层，边界必须先划清楚。

完全可配
工序顺序 · 节点参数 · 超时时间 · 失败策略 · 是否启停
以及：一条线复制成另一条线，换工件换套流程
只能选
这一步调用哪个子程序 · 参数填什么值 · 失败走哪条路
必须写代码
子程序内部逻辑 · PLC 握手 · CNC 坐标计算 · 扫码解析 —— 这些永远是 C# + 原生 DLL

能实现的六件事

能力现在之后
现场调参班组长找你改代码页面自己改超时、重试、失败策略
追查问题只知道“跑了”，不知第几步失败每节点有起止时间、退出码、失败原因
新增一个工步改 5 处 + 编译 + 部署，2–3 小时页面填表，10 分钟，不改一行代码
一条线复制成另一条复制整个项目，逐处改机床号复制流程模板，只改机床参数
换工件换工艺只有一套流程，或手工改配置多套流程模板，切换即用
改超时时间改 flow.json 或代码 + 重启属性面板改，保存即生效
最有价值的是前两条。现场调参 = 把改动权限从开发下放到工艺；追查问题 = 出质量问题时能不能说清楚。

做不到的

  • 新工步的执行逻辑还是要写 C# —— 低代码管“什么时候调、用什么参数、失败怎么办”，不管“内部怎么实现”
  • 不做分支、并行、循环 —— 只做线性顺序，要分支就得加表达式引擎和调试器，成本翻倍
  • 不能跨机床品牌通用 —— 执行层绑死 Fwlib32 / OpcUa 这些 DLL
  • 不能当产品卖给别的厂 —— 单机、无多租户、无权限体系
  • 不能生成实时曲线、3D 视图 —— 那些还是要写前端

9已知隐患

隐患影响建议
5 份副本无版本管理改坏无法回滚优先补 Git（半天）
子程序 Main() 返回 void拿不到真实执行结果，只能判断“进程退了”，判断不了“这步成功了”改 static int Main 返回退出码。优先级高于所有界面工作
script.js 93 KB 全局变量改动影响面靠人脑推不重构，改前先 grep 引用
Vue 2.7.14 已 EOL无安全更新不在其上追加新功能
三个编排页并存维护分叉定一份主线，其余归档
零测试、零文档新人无法接手先写回归清单（10 条手动路径）
关于“不规范”的判断：这套系统缺的是保护机制（版本、测试、文档、部署），不是设计方向错了。多进程隔离在产线上是正确设计 —— 一个子程序崩了不拖垮主程序。所以要补保护，不要推倒重来。

10推进阶段

界面到“能配”是 2–3 周的事，但执行侧（子程序改造 + 现场验证）压不掉，总周期按 3 个月排。

阶段大概干什么交付物
P0 定规矩2 周想清楚一个环节要哪些参数schema-design.md
P1 元数据层2 周环节、流程改成从配置读，删掉 GROUPS节点/流程 CRUD 接口
P2 渲染引擎2 周给份配置就能自动长出界面150 行渲染器
P3 设计器2 周拖拽能保存、重开能回显闭环的设计器
P4 执行引擎3 周子程序改造 + 调度 + 状态回传一条线端到端跑通
P5 收口2 周老数据能升级、能演示迁移机制 + 文档
顺序建议调整：先把子程序 Main 返回值改掉，再回头补界面。否则界面做得再漂亮，也跑不出真实结果。
